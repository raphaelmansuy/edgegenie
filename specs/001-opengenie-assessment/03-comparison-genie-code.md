# 03 · OpenGenie against Databricks Genie Code

The comparison the README asks a reader to accept. It is done here row by row, with the Genie Code
side **quoted from the documentation dated 9 November 2026** and the OpenGenie side **cited to a file
and line on commit `2063af3`**. Every row ends in one of five verdicts, defined once:

| Verdict | Meaning |
|---|---|
| **Genie** | Genie Code has it; OpenGenie does not and cannot cheaply |
| **Parity** | Both have it, comparably |
| **OpenGenie** | OpenGenie has it and Genie Code does not, or does it materially worse |
| **Different** | Both have something here and they are not the same thing; the row explains |
| **?** | Not established. The documentation does not say, and this assessment did not drive the product |

A row marked **Genie** is not automatically something to build. [05](05-gaps-and-improvements.md)
decides that, and refuses several.

---

## 1 · The framing problem

`specs/006-databricks/README.md` is titled **"On par with Genie Code"**, and `README.md` opens with
*"Genie Code is the best coding agent for data engineering … OpenGenie is an open-source Databricks
App that gives a coding agent the same kind of workspace context"*. Both are narrower and more honest
than "on par", and the difference matters for this comparison:

* Genie Code is **not a coding agent that also does data**. It is *"the AI coding and data assistant
  for developers and technical practitioners in the Databricks workspace"*, and it says of itself:
  *"Code generated by Genie Code is intended to run in a Databricks compute environment … **It is not
  intended to be a general-purpose programming assistant.**"*
  — [Features and capabilities](https://docs.databricks.com/aws/en/genie-code/features-capabilities), 9 Nov 2026
* OpenGenie is **a general coding agent placed inside a Databricks workspace**, with the workspace as
  its tool surface. It is closer to Claude Code with a Databricks MCP server than to Genie Code.

So the right question is not "is OpenGenie as good as Genie Code". It is: **for each class of work, which
one is the better tool, and what would it cost to close the gap on the other?**

| Class of work | Share (est.) | Better today | Why |
|---|---|---|---|
| Notebook and pipeline code, debug, refactor | ~55% | **OpenGenie** on cost and model choice; **Genie** on speed of first contact | Genie has zero setup and inline completions; OpenGenie has the model lever and the evidence loop |
| Business-term analysis ("what was revenue in EMEA") | ~20% | **Genie** | Genie Ontology; OpenGenie has no equivalent (`[G-7]`) |
| Governance-critical work (audit, regulated change) | ~15% | **OpenGenie** | Per-call evidence, immutable turn pins, an append-only journal, a fence. Genie's classifier is explicitly *not* a security boundary |
| Unattended / scheduled work | ~10% | **Genie** | Genie Code scheduled tasks are GA; OpenGenie's agent only runs when a browser asks |

That split is the honest answer and it is what [05](05-gaps-and-improvements.md) builds on.

## 2 · Capability register

The register from `specs/006-databricks/14-genie-code-gap-analysis.md` (C1–C15) is extended here to
**C1–C26** because Genie Code shipped a great deal in 2026 that the original register predates: the
full-page command centre, parallel chats, chat branching, scheduled tasks, sharing with ACLs, memory,
user and workspace skills, a level-of-effort control, and `ug`-based agent configuration. A comparison
against the 2025 product would flatter OpenGenie.

Each row: **what Genie Code does** (quote), **what OpenGenie does** (file), **verdict**, **note**.

| **C8** | **Feedback** (Useful / Not useful) | None | **Genie**, low value. `[G-14]` |

### 2.2 Context and grounding

| # | Genie Code | OpenGenie | Verdict |
|---|---|---|---|
| **C10** | **Unity Catalog grounding** automatic: *"uses Unity Catalog metadata (tables, columns, descriptions, and your company's popular data assets)"* | Explicit tools the agent must call: `dbx_describe_table`, `dbx_search_tables`, plus a written rule in `AGENTS.md` *"Your FIRST tool call for any data task must be `describe_table` on every table you will read"* (`agent_config.py:272-313`) | **Parity in outcome, opposite in mechanism** — and OpenGenie's is *checkable*: the call appears in the transcript and in the evidence table. Genie's is invisible |
| **C11** | **Genie Ontology**: modeled knowledge (metric views, domains, Pages, certification) and learned knowledge (from dashboards, SQL, Genie Agents), shared with external agents through **Genie One MCP** — [docs](https://docs.databricks.com/aws/en/genie/genie-ontology/) | **Nothing.** The `genie` scope is declared in `databricks.yml` and no code calls a Genie API (`rg 'api/2.0/genie'` → none) | **Genie** — the largest capability gap, and the cheapest to close (it is one MCP server). `[G-7]` |
| **C12** | **Documentation search with citations**: *"Genie Code searches Databricks documentation … You can ask Genie Code to cite its sources"* | None. No doc-search tool, no citation rendering in `Transcript.tsx` | **Genie** — and the repository *owns* a documentation site it could index. `[G-9]` |
| **C13** | **`AGENTS.md` / `CLAUDE.md` auto-discovery**: *"Genie Code can also automatically discover AGENTS.md and CLAUDE.md files within your project"* | **Writes** an `AGENTS.md` into the agent's cwd (`agent_config.py:170-182`) and never **reads** the user's. `rg 'AGENTS.md' api` → the writer only | **Genie** — and this is the highest-value cheap fix in the whole list: the workspace already has a `AGENTS.md` convention. `[G-5]` |
| **C14** | **Custom instructions**, user and workspace scope | None. The working agreement is generated from the session's scope only | **Genie** — `[G-5]` covers this with C13 |
| **C15** | **Agent skills**, personal (`~/.assistant/skills/`) and workspace (`Workspace/.assistant/skills/`), auto-loaded or `@`-mentioned, plus *"tell Genie Code to capture it as a skill"* | **4 built-in skills** shipped in the repo, read through `dbx_skill` (`tools/skills/*.md`, `tools/…:2488-2506`). No user skill, no workspace skill, no capture | **Genie** — OpenGenie has *skills* as a mechanism and none of the *authoring* that makes them useful. `[G-6]` |
| **C16** | **Persistent memory across sessions** | None. Every conversation starts from nothing; the journal is not read back into a prompt | **Genie** — `[G-10]` |
| **C17** | **MCP: managed, UC-registered, custom on Apps**, plus a marketplace in settings and **managed OAuth for Google Drive / SharePoint / GitHub** (beta) | One MCP server, injected at `session/new` (`runtime.py:125-126`). No additional server can be attached, no marketplace, no connectors | **Different** — OpenGenie's single server is *fenced*, which no third-party server is. Adding arbitrary MCP would forfeit the fence. `[RB-7]`, `[G-11]` |
| **C18** | **Attach files** `.png .jpg .jpeg .gif .webp .pdf .csv .xlsx .xls .json .jsonl`; *"By default, Genie Code uses attached files only in the current chat and does not save them"* | Images, PDF, text/CSV/code, `.ipynb` — magic-byte checked, 8 MB each, 24 MB total, 6 per message (`domain/blob.py:28-29,228-236`). **No `.xlsx`/`.xls`** | **Different** — OpenGenie's is stricter and better validated (magic bytes, cross-family mismatch refusal, vision-aware copy) and lacks two spreadsheet types. `[G-12]` |
| **C19** | **Serverless code execution**, and in notebooks the code runs *in the notebook* with cell output fed back | SQL runs on a warehouse as the user. **Python runs on serverless as the app's service principal, administrators only** (`pyrun_service.py`, `python_run_policy` at `api.py:965-977`) | **Different** — a deliberate and correct choice (running arbitrary code as the app's identity is a hole, and the code says so), and it means most users cannot execute Python at all. `[G-13]` |

### 2.5 Control, safety and audit

This is the section where the comparison reverses.

| # | Genie Code | OpenGenie | Verdict |
|---|---|---|---|
| **C31** | **Approval modes**: Ask every time / Allow in this chat / Always allow / **Auto-approve with an AI classifier**. And, verbatim: *"Auto-approve is a productivity feature, not a security boundary. The classifier is a best-effort heuristic that can be wrong … Do not rely on it to enforce security, compliance, or access-control requirements."* | ACP's `session/request_permission` surfaced **inline** with three outcomes (`allow_once`, `allow_session`, `deny`), matched server-side against the options the agent actually offered (`orchestrator.py:1216-1234`) — so an approval cannot be forged into a different option | **OpenGenie** on rigour. Genie's is a classifier that says it cannot be trusted; OpenGenie's is an explicit decision bound to an offered option. **Caveat:** writes inside the schema are not gated at all (`F-8`) |
| **C32** | **Unity Catalog permissions** govern everything; *"it can only access data and perform operations that you have permissions for"* | Same boundary, and *closer* to it: the tool server calls **as the signed-in user** with a forwarded token (`orchestrator.py:618-666`, `tools/…:_token`). Unity Catalog is the ACL, not a re-implementation | **Parity**, and OpenGenie's is auditable per call |
| **C33** | **Budgets** per account/workspace/group/user: *"Budgets for Unity Gateway provide a near real-time estimate … **Do not use this feature as a way to ensure an absolute spend cap**"* | No budget concept. The levers are model choice (13 models), the tool budget (28), and the turn/time limits (`MAX_TURNS`, `session_max_run_seconds`) | **Different** — Genie has a ceiling it admits is approximate; OpenGenie has a *lever* and no ceiling. `[G-20]` |
| **C34** | **Cost**: DBU-metered, 150 DBU/user/month free, 25% promo to 31 Jan 2027, **service principals get no allowance** — [monitor cost](https://docs.databricks.com/aws/en/genie/monitor-cost) | **Per-token, per-provider**, on whichever model you choose, with envelope-encrypted per-user keys (`adapters/llm/vault/`). No DBU, no promo, no allowance | **OpenGenie** on controllability. **No cost comparison is made** — the repository holds no Genie billing data (`docs/genie-code-replacement-spec.md §9.3`) |
| **C35** | **Audit**: Unity Gateway records model and MCP usage; Unity Catalog records data access | **An append-only journal the app owns**: `agent.session_event`, monotonic `seq`, one row per event, redacted before insert; **plus** `llm.llm_turn_model` pinning which model answered which turn; **plus** the evidence table matching each requirement to the tool call that proved it | **OpenGenie**, clearly. This is the product's moat. Genie's audit lives in platform tables you query; OpenGenie's lives in the conversation and is rendered as proof |
| **C36** | **Memory and context** managed by Databricks (managed agent memory is a Beta in the release notes) | None (`C16`) | **Genie** |
| **C37** | **Centrally configure coding agents** (release notes, 2026) | `databricks.yml` + `app.yaml` + `APP_LLM_ADMINS`: an administrator names who may change the catalogue, and the KEK is a secret resource | **Different** — Genie governs *agents*; OpenGenie governs *this app's* model catalogue |

*(Rows overlap in a few cells because a row can be parity on one axis and different on another; the
count is by the verdict column as written.)*

That is the honest picture, and it is not flattering. **Genie Code is a bigger product.** It has been
built by a company with the workspace, the identity system, the ontology, and the BI surfaces in-house,
and it now has a command centre, parallel threads, branching, scheduling and sharing.

**But three of OpenGenie's four wins are structural**, not features:

1. **Model freedom** — Genie cannot offer it, because its whole business is metering its own inference.
2. **An audit trail the customer owns**, with per-requirement evidence. Genie's equivalent is a
   platform table the customer queries, not a proof attached to the answer.
3. **A fence that is a mechanism** (a process started with one folder and one schema) rather than a
   classifier the vendor itself says not to trust.

And one is a *cost* property that Genie's own documentation concedes: budgets are a ceiling, not a cap.
OpenGenie's lever is the model.

## 5 · Two honest paragraphs

**What Genie Code's existence says about this product.** Genie Code proved the market: an agent inside
the workspace, grounded in Unity Catalog, is worth paying for, and *"Genie products have grown over
10x and are used by 90% of Databricks customers"* (Summit 2026 blog). OpenGenie exists because two
decisions inside that product are not negotiable for a customer — the model and the bill — and both
are the *reason* the product is metered. That is a real gap and it is not going away.

**What OpenGenie should stop claiming.** "On par" is not true and cannot be made true without building
a BI surface, an ontology, a connector marketplace and a scheduler. What *is* true, and is a stronger
claim, is: **"the governed coding agent you can prove."** Every tool call is attributable to a user,
every answer to a tool call, and every model choice to a turn. No competitor — Genie Code, Claude
Code, Codex or Cursor — ships that as a first-class concept. The product should lead with it.
