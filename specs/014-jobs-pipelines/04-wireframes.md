# 04 · Wireframes

Every screen this spec adds, every state each one can be in, and every recovery path. The frames are
**generated** by [`e2e/build_wireframes.py`](e2e/build_wireframes.py) and checked by
`node scripts/verify-spec-ascii.mjs`, so a box cannot drift by one column without failing a command.
Edit the generator, not this file.

Two conventions the generator enforces, both learned from the verifier:

* **A border is a line, not a place for text.** A section title is a row inside the frame
  (`── Last run ─────`), never a label welded into `┌...┐`.
* **A multi-pane layout is one frame with `│` gutters**, not three boxes side by side. A second box's
  right border reads as content escaping the first, which is exactly what it looks like.

What each frame is for:

| Frame | Screen | The question it answers |
|---|---|---|
| F1 | the shell, `Data` selected | where jobs and pipelines live |
| F2 | a job page | is my job working, and when will it run? |
| F3 | a run page | what happened to each task? |
| F4 | a pipeline page | did the last update succeed? |
| F5 | a run in flight | is it stuck, or just working? |
| F6 | a refusal | what can I do about a permission wall? |
| F7 | four empty states | is "nothing" a fault? |
| F8 | two narrow widths | does it survive a small window? |
| F9 | navigation | how do I get to any of this? |

The widths in F8 are `modeFor`'s, read from `web/src/domain/layout.ts`: mid is ≤ 1180 px, narrow is
≤ 820 px, and `CENTRE_MIN` is 480 px. A drawing that claims otherwise is wrong — 013's S7 found one.

## What every frame has in common, and why

**One state word, always present.** Each header carries the object's state as a word, not only as a
colour. The word comes from a pure function over the payload (`runWord`, `pipelineWord`), so the same
table drives the page, the rail row and the transcript's chip. Colour reinforces; it never carries the
meaning alone.

**The last run outranks the definition.** A job page leads with what happened, not with what is
configured, because "is it working?" is the question that brought the user here. The configuration is
below it, complete, for the day the user needs to change it.

**A value that could not be read renders `—`.** Never `0`, never `ready`, never a blank that reads as
zero. F6's Schedule block is the demonstration: the block says it was not read and why, instead of
showing a cron it does not have.

**Every control that spends money says so.** Run now names the compute and the expected duration.
Full refresh names the tables it will re-read. Resume schedule says, in its confirmation, that it
creates a recurring cost. Stop asks, because it abandons work in flight.

**Nothing animates as its only signal.** A spinner with no label is the shape of a stuck page. Every
in-flight state has a sentence: "still running", "polling every 3 s", "a cold start is a state, not a
failure".

## What is deliberately absent

| Absent | Why |
|---|---|
| A DAG picture with edges drawn as lines | A node-link diagram in a 470 px column is unreadable at the sizes this app runs; levels plus an explicit `after X` on each task carries the same information and stays selectable text |
| A log viewer | Spark logs are gigabytes and live behind the cluster; the page links out and quotes the error it has |
| A schedule editor with a cron builder | The agent writes the cron; the page shows it and toggles its pause state. A cron builder is its own product |
| A "Run with parameters" form | `run-now` accepts parameters, and a form that posts arbitrary JSON into a job is a fence hole; the agent does it through a tool, where the fence applies |
| A sparkline of past runs on the job page | It is the one thing in Databricks' own Jobs list that reads at a glance, but it needs `runs/list` per job; the Run list block gives the same history for one job, one page, no fan-out |
